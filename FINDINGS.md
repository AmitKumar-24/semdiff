| F-008 | T-16 | docs.python.org (corpus fixture `docs-python-org-001`) rebuilds daily and prints `Last updated on Sep 17, 2026 (02:47 UTC).` — a human-readable date + `(HH:MM UTC)`, which is neither ISO-8601 nor relative phrasing, so FR-9 as written does not cover it. | F-009 | T-17 | Full normalization (parse + all five families) takes 54–520 ms on the five T-04 captures (docs.python.org 110 KB: 519 ms, 978 whitespace applications) — 1.5–5× over the NFR-3 sub-100 ms target for the parse+normalize path. Likely cost: `Locator.for_node` builds a positional CSS path per application (a parent walk with sibling counting). Profile before T-19/T-21 and consider lazy or cheaper locators; not a T-17 correctness issue. |
| F-010 | T-19 | `canonical.whitespace` collapses **non-ASCII** whitespace: its `_WS` pattern is `\s+`, which is Unicode-aware in Python, so U+00A0 (`&nbsp;`), U+2009 and friends count as collapsible layout. The HTML spec collapses only ASCII whitespace; `&nbsp;` is content. Consequence: `normalize("<p>a&nbsp;b</p>") == normalize("<p>a b</p>")`, so a real nbsp/space edit is invisible to the diff. **Resolved in the T-19 change set (D-035):** `_WS` is now `[\t\n\f\r ]+` and `canonical.whitespace` is at `version = 2`. |
| F-011 | T-19 | `semdiff.normalize` (the function) shadows the `semdiff.normalize` **subpackage** attribute, exactly as `semdiff.parse` already shadows `semdiff/parse.py`. `from semdiff.normalize import X`, `importlib.import_module` and deep submodule imports all still work, but `import semdiff.normalize as x` binds the *function*, and pytest's string-target `monkeypatch.setattr("semdiff.normalize.registry....")` no longer resolves (two tests now pass the module object instead). Pre-existing pattern, required by FR-10 + D-030; the alternative is renaming the subpackage to `semdiff._normalize`. |
| F-012 | T-19 | Performance baseline for F-009, measured through the public API on the five T-04 captures (best of 5, 3.12): 122 / 171 / 203 / 282 / 550 ms total, of which parse is only 2.5–11.9 ms. **>95% of the cost is the rule engine**, not parsing — so F-009's suspicion (`Locator.for_node` per application, 249–1652 applications per page) is where to look. Still 1.2–5.5x over NFR-3. **Corrected at T-23:** re-measuring the same five captures on a quiet machine gives 32 / 43 / 53 / 129 / 171 ms — 3–4x faster with *more* rules running and no change to `Locator` or the engine hot path, so the T-19 figures were inflated by machine load and are not a usable baseline. Three of five captures now sit inside the NFR-3 100 ms budget; ant.design (576 KiB) and docs.python.org remain over. Any future optimization work must benchmark against a quiet machine and report a distribution, not a single run. |
| F-013 | T-04 | **Hashed asset URLs are the dominant real-world deploy noise and no family covers them.** On the 2026-09-25 re-capture they are the *only* difference in docusaurus.io (two `<script src>` bundle hashes; the rest of the document is byte-identical) and the main one in mui.com (3 chunk hashes, the Next.js `buildId` in two `src`s and again inside `__NEXT_DATA__`, plus one `<link rel="preload">` reordered). docs.python.org adds the query-string variant (`pydoctheme.css?v=4365c8fe` → `?v=c60eaebf`) and ant.design the same in `/umi.da948370.js`. FR-5 covers `class`, FR-6 covers `id`, FR-7 covers tokens — nothing covers `src`/`href`/`srcset`. Blocks the noise-only admission of two otherwise-perfect pairs (Q-23). **Addressed in T-23** (FR-44, D-036/D-037): docusaurus.io now normalizes identically; mui.com does not, because its `buildId` also sits inside `__NEXT_DATA__` (protected) and one preload link is reordered — both deliberately out of scope. |
| F-014 | T-04 | ant.design emits `<meta name="build-time" content="1789367183442">` and `<meta name="build-hash" content="db0488c1…">`, both changing every deploy. These are a timestamp and a hash in **attribute** position; FR-9's rules are TEXT-target only and FR-6 is scoped to `id`, so neither fires. Same shape as F-008 (a timestamp the family does not reach), different position. Confirmed at T-23: the same two values are also embedded in an inline `window.__UMI_METADATA_LOADER_DATA__` script, which D-029 protects, so even a `<meta>` rule would leave ant.design's pair differing. |
| F-015 | T-04 | storybook.js.org streams its React Server Component payload as ~400 `<script>self.__next_f.push([1,"…"])</script>` calls, and the *chunk boundaries* shift between deploys even where the payload is equivalent: 418 of 1582 normalized tokens differ. Script content is protected by design (D-029), so normalization can never neutralize this. Any RSC/streamed-payload site is structurally unsuitable as a noise-only fixture unless the corpus rule allows ignoring `<script>` bodies — which would weaken the protection that makes JSON-LD extraction trustworthy. |
| F-016 | T-04 | A 7-day interval on actively maintained sites produces **real** content changes, not just noise: ant.design bumped a version string (`6.6.4` → `6.6.5`), docs.python.org reworded a paragraph and added a `<div class="admonition note">` block, storybook.js.org's GitHub star counter moved (`91,045` → `91,144`). Three of the five pairs are disqualified from `noise_only` on content grounds alone. A noise-only corpus needs either a much shorter interval (hours, catching a redeploy without an edit) or pages that are not living documentation. |
